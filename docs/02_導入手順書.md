## 0. 事前準備

### 0.1 必要な権限

| 対象 | 必要権限 | 保有者 |
|---|---|---|
| Azureサブスクリプション | 対象リソースグループの共同作成者 | 構築担当 |
| 同上 | ロール割り当て権限（ユーザーアクセス管理者 または 所有者） | 構築担当またはAzure管理者 |
| Microsoft Entra ID | アプリケーション登録の作成権限 | Entra管理者 |
| Azure DevOps Organization | Project Collection Administrators（PCA） | ADO管理者 |

> ロール割り当て権限がない場合は、STEP 3 を Azure管理者に依頼する形で分割実施できます（`-SkipRoleAssignment` オプションを使用）。

### 0.2 必要なツール

| ツール | バージョン | 用途 |
|---|---|---|
| Azure CLI | 2.60 以降 | 基盤デプロイ |
| PowerShell | 5.1 以降（7.x推奨） | スクリプト実行 |
| Self-hosted Agent（任意） | 使用する場合は構築済みのもの | Pipeline実行（既定はMicrosoft-hosted） |

## STEP 1. サービスプリンシパルの作成

証跡取得専用のIDを作成します。**読み取り専用**とすることで、証跡取得処理自体が証跡を改変できないことを監査人に説明できます。

### 1-1. アプリケーション登録

```powershell
az login --tenant <テナントID>
az account set --subscription <サブスクリプションID>

# 証跡取得専用のアプリ登録を作成
az ad app create --display-name "sp-ado-audit-export" -o json
```

出力された `appId` と、続けて取得する `id`（オブジェクトID）を控えます。

```powershell
$appId = "<上で取得した appId>"
az ad sp create --id $appId -o json
```

出力された **オブジェクトID（`id`）** を控えてください。STEP 3 のロール割り当てで使用します（`appId` ではない点に注意）。

### 1-2. 確認事項

| 項目 | 値 | 記録欄 |
|---|---|---|
| 表示名 | `sp-ado-audit-export` | |
| アプリケーションID（クライアントID） | | |
| オブジェクトID（サービスプリンシパル） | | |

## STEP 2. Log Analytics 基盤のデプロイ

カスタムテーブル4種と Data Collection Rule を作成します。

### 2-1. デプロイ実行

```powershell
cd <リポジトリ展開先>\ado-audit-archive\infra

.\Deploy-AuditArchive.ps1 `
    -SubscriptionId <サブスクリプションID> `
    -ResourceGroupName <リソースグループ名> `
    -WorkspaceName <ワークスペース名> `
    -IngestionPrincipalObjectId "<STEP 1-1 のオブジェクトID>"
```

ロール割り当て権限を持たない場合：

```powershell
.\Deploy-AuditArchive.ps1 `
    -SubscriptionId <サブスクリプションID> `
    -ResourceGroupName <リソースグループ名> `
    -WorkspaceName <ワークスペース名> `
    -SkipRoleAssignment
```

### 2-2. 出力値の記録

スクリプト完了時に以下が出力されます。**STEP 5 の変数グループで使用します。**

| 変数名 | 例 | 記録欄 |
|---|---|---|
| `LAW_DCR_ENDPOINT` | `https://dcr-xxxx.japaneast-1.ingest.monitor.azure.com` | |
| `LAW_DCR_IMMUTABLE_ID` | `dcr-xxxxxxxxxxxxxxxxxxxxxxxxxxxx` | |
| `LAW_DCR_RESOURCE_ID` | `/subscriptions/.../dataCollectionRules/dcr-ado-audit` | |
| `LAW_CUSTOMER_ID` | ワークスペースGUID | |

### 2-3. デプロイ結果の確認

```powershell
# テーブルが4つ作成されたこと、保持期間が設定されたことを確認
az monitor log-analytics workspace table list `
    --resource-group <リソースグループ名> `
    --workspace-name <ワークスペース名> `
    --query "[?starts_with(name,'ADO_')].{Name:name, Interactive:retentionInDays, Total:totalRetentionInDays}" `
    -o table
```

**期待結果**

| Name | Interactive | Total |
|---|---|---|
| ADO_Approval_CL | 730 | 1095 |
| ADO_ExportAudit_CL | 730 | 1095 |
| ADO_PipelineRun_CL | 730 | 1095 |
| ADO_PullRequest_CL | 730 | 1095 |

## STEP 3. ロールの割り当て（STEP 2 で実施済みの場合は省略）

Azure管理者へ以下を依頼します。

```powershell
az role assignment create `
    --assignee-object-id "<STEP 1-1 のオブジェクトID>" `
    --assignee-principal-type ServicePrincipal `
    --role "Monitoring Metrics Publisher" `
    --scope "<LAW_DCR_RESOURCE_ID>"
```

検証ステージでKQLを実行するため、ワークスペース参照権限も付与します。

```powershell
az role assignment create `
    --assignee-object-id "<STEP 1-1 のオブジェクトID>" `
    --assignee-principal-type ServicePrincipal `
    --role "Log Analytics Reader" `
    --scope "/subscriptions/<サブスクリプションID>/resourceGroups/<リソースグループ名>/providers/Microsoft.OperationalInsights/workspaces/<ワークスペース名>"
```

> **依頼時の説明文（そのまま使用可）**
> 「Azure DevOpsの変更承認証跡をLog Analyticsへ長期保管するための専用IDです。付与するのはData Collection Ruleへのデータ送信権限（Monitoring Metrics Publisher）と、検証用の読み取り権限のみで、既存リソースへの変更権限は含みません。」

## STEP 4. Azure DevOps 側の権限付与

作成したサービスプリンシパルを、Azure DevOps組織に**読み取り専用**で追加します。

### 4-1. 組織へのユーザー追加

1. `https://dev.azure.com/<組織名>/_settings/users` を開く
2. 「ユーザーの追加」をクリック
3. **ユーザーまたはサービスプリンシパル**：`sp-ado-audit-export`（アプリケーションIDでも検索可）
4. **アクセスレベル**：`Basic`
5. **プロジェクト**：証跡取得対象の全プロジェクト
6. 「追加」をクリック

### 4-2. 権限の絞り込み（読み取り専用化）

1. `Organization Settings` → `Permissions` を開く
2. 新規グループ `ADO-Audit-Export-Readers` を作成
3. 作成したサービスプリンシパルを当該グループに追加
4. 各プロジェクトの `Project Settings` → `Permissions` で、当該グループに以下のみを許可

| 権限 | 設定 |
|---|---|
| View project-level information | Allow |
| Read（Repositories） | Allow |
| View builds / View build pipeline | Allow |
| その他の書き込み系権限 | **未設定（Not set）のまま** |

### 4-3. 疎通確認

```powershell
$token = (az account get-access-token --resource 499b84ac-1321-427f-aa17-267ca6975798 -o json | ConvertFrom-Json).accessToken
Invoke-RestMethod -Uri "https://dev.azure.com/<組織名>/_apis/projects?api-version=7.1" `
    -Headers @{ Authorization = "Bearer $token" } | Select-Object -ExpandProperty value |
    Select-Object name, id
```

> ⚠️ プロジェクト一覧ではなくHTMLのサインインページが返る場合は、組織へのユーザー追加が未反映です。数分待って再実行してください。

## STEP 5. Azure DevOps 側の構成

### 5-1. リポジトリへの配置

証跡取得の仕組み自体も変更管理の対象とするため、専用リポジトリに配置します。

1. Azure DevOps Organization に新規プロジェクト（または既存の基盤管理プロジェクト）を用意
2. リポジトリ `ado-audit-archive` を作成
3. パッケージの内容を `main` ブランチに配置

```
ado-audit-archive/
├── infra/
├── scripts/
├── pipelines/
├── kql/
└── docs/
```

4. **`main` ブランチにブランチポリシーを設定**（最小レビュアー数1以上）
   → 証跡取得ロジック自体の変更も統制下に置くため、監査上重要です。

### 5-2. サービス接続の作成

1. `Project Settings` → `Service connections` → `New service connection`
2. `Azure Resource Manager` → `Workload Identity federation (manual)` を選択
3. 以下を入力

| 項目 | 値 |
|---|---|
| Subscription ID | `<サブスクリプションID>` |
| Subscription Name | （該当サブスクリプション名） |
| Service Principal Id | STEP 1 のアプリケーションID |
| Tenant ID | `<テナントID>` |
| Service connection name | `sc-ado-audit-export` |

4. 画面に表示される **Issuer** と **Subject identifier** を控える
5. Entra ID側でフェデレーション資格情報を登録

```powershell
$appId = "<アプリケーションID>"
$credential = @{
    name = "ado-audit-export"
    issuer = "<画面に表示された Issuer>"
    subject = "<画面に表示された Subject identifier>"
    audiences = @("api://AzureADTokenExchange")
} | ConvertTo-Json -Depth 3

$credential | Out-File -FilePath .\fedcred.json -Encoding ascii
az ad app federated-credential create --id $appId --parameters .\fedcred.json
Remove-Item .\fedcred.json
```

6. Azure DevOps画面に戻り `Verify and save`
7. 作成後、`Security` から当該Pipelineのみに使用を限定

### 5-3. 変数グループの作成

`Pipelines` → `Library` → `+ Variable group`

| 変数名 | 値 | シークレット |
|---|---|---|
| グループ名 | `ado-audit-archive` | － |
| `ADO_ORGANIZATION` | `<組織名>`（例：`contoso`） | いいえ |
| `AZURE_SERVICE_CONNECTION` | `sc-ado-audit-export` | いいえ |
| `LAW_DCR_ENDPOINT` | STEP 2-2 の値 | いいえ |
| `LAW_DCR_IMMUTABLE_ID` | STEP 2-2 の値 | いいえ |
| `LAW_CUSTOMER_ID` | STEP 2-2 の値 | いいえ |
| `ADO_PROJECT_FILTER` | （空欄＝全プロジェクト対象） | いいえ |

> 本方式ではシークレットを保持しません。変数グループに機密情報が含まれないことも監査上の説明材料になります。

### 5-4. Pipelineの作成

1. `Pipelines` → `New pipeline` → `Azure Repos Git`
2. リポジトリ `ado-audit-archive` を選択
3. `Existing Azure Pipelines YAML file` → `/pipelines/azure-pipelines-ado-audit-export.yml`
4. パイプライン名を `ADO-Audit-Export` に変更して保存
5. `Edit` → `Triggers` → `Variables` から変数グループがリンクされていることを確認

### 5-5. エージェントプールの確認

YAMLの既定は Microsoft-hosted agent（`windows-latest`）です。

```yaml
pool:
  vmImage: windows-latest
```

Self-hosted Agentを使用する場合は、実際のプール名に合わせて次のように置き換えます。

```yaml
pool:
  name: <セルフホステッドプール名>
```

## STEP 6. 初回実行（ドライラン）

### 6-0. オフライン自己テスト（任意・推奨）

Azure接続を伴わずに抽出ロジックを確認できます。環境構築前でも実行可能です。

```powershell
cd <リポジトリ展開先>\ado-audit-archive
.\scripts\Invoke-OfflineSmokeTest.ps1
```

**期待結果**：`ALL TESTS PASSED`（36ケース）

> エージェントのタイムゾーンがJSTであっても抽出期間がUTCで正しく送信されることを検証するケースを含みます。エージェント移設時にも実行することを推奨します。

### 6-1. ドライラン実行

取込を行わずに抽出のみを確認します。

1. `Pipelines` → `ADO-Audit-Export` → `Run pipeline`
2. パラメータを以下に設定

| パラメータ | 値 |
|---|---|
| Export mode | `custom` |
| Window start (UTC) | `2026-09-12T00:00:00Z` |
| Window end (UTC) | `2026-09-19T00:00:00Z` |
| Dry run | ✅ **オン** |
| Include PR branch policy evaluations | ✅ オン |

3. 実行後、ログに以下が出力されることを確認

```
Projects in scope: N
Extracted totals - PR: xx, Runs: xx, Approvals: xx
Archive written: ...
SHA256        : ...
WhatIf: would send xx record(s), xxxx bytes to Custom-ADO_PullRequest_CL
```

4. `Artifacts` から `ado-audit-evidence-<BuildId>` をダウンロードし、JSONの中身を目視確認

## STEP 7. 本番実行

1. 同じパラメータで **Dry run を オフ** にして実行
2. Exportステージ成功後、Verifyステージが自動実行される
3. Verifyステージのログで全項目が `[PASS]` であることを確認

```
[PASS] Self-audit row present - Status=Succeeded; BuildId=1234; TimeGenerated=...
[PASS] Row count reconciliation: ADO_PullRequest_CL - expected 12, found 12; waited 0s
[PASS] Row count reconciliation: ADO_PipelineRun_CL - expected 45, found 45; waited 0s
[PASS] Row count reconciliation: ADO_Approval_CL - expected 8, found 8; waited 0s
[PASS] Archive hash matches ingested self-audit row - export-result, Log Analytics, and archive SHA256 values are consistent
[PASS] Approval records carry approver and timestamp - total 8, missing approver 0, missing timestamp 0
[PASS] Export job completed without errors - Succeeded
All verification checks passed.
```

> ⚠️ 新規カスタムテーブルへの初回取込は、クエリ可能になるまで最大15分程度かかります。Verifyステージは最大15分ポーリングします。それでもデータが見えない場合は、時間をおいてVerifyステージのみ再実行してください。

## STEP 8. スケジュール有効化

YAML内の `schedules` により自動で有効化されますが、以下を確認します。

1. `Pipelines` → 対象Pipeline → `...` → `Scheduled runs`
2. 以下2件が表示されること

| スケジュール | 次回実行 |
|---|---|
| Daily incremental export (02:00 JST) | 毎日 02:00 JST |
| Monthly full re-scan (03:00 JST on the 2nd) | 毎月2日 03:00 JST |

> cron式はUTCです。JSTとの対応は `0 17 * * *` → 翌日02:00 JST、`0 18 1 * *` → 毎月2日03:00 JST となります。
